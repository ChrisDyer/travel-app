# Phase 2 — Feed route, proxy allowlist, management API

**Read `00-overview.md` first**, then `PROGRESS.md` to see what Phase 1 actually delivered.

Phase 2 makes the feed fetchable: the public route, the `feeds.ts` data layer, the one-line
allowlist in `src/proxy.ts`, and the three management endpoints the Phase 3 UI will call. **No

## 1. `src/lib/calendar/feeds.ts`

DB layer, no test file.

```ts
export interface CalendarFeedRow {
  id: string; userId: string; slug: string; name: string; token: string;
  filters: string; lastFetchedAt: string | null; lastFetchedUserAgent: string | null;
  tokenRotatedAt: string | null; createdAt: string; updatedAt: string;
}

/** Returns the shared feed, creating it on first call. Idempotent. */
export function ensureFeed(userId: string): CalendarFeedRow;
export function getFeedByToken(token: string): CalendarFeedRow | null;
export function updateFeed(id: string, patch: { name?: string; filters: string }): void;
export function rotateFeedToken(id: string): { token: string; tokenRotatedAt: string };
export function recordFetch(id: string, userAgent: string | null): void;
```

- `ensureFeed` inserts `slug: 'shared'` with `newFeedToken()` and `serializeFeedFilters(DEFAULT_FILTERS)`.
  Use `INSERT ... ON CONFLICT(user_id, slug) DO NOTHING` then `SELECT`, so two concurrent first
  page loads cannot create two rows or throw.
- `recordFetch` writes `last_fetched_at` and a **truncated** user agent (cap ~200 chars — it is
  attacker-controlled text going into your database and later onto the Settings page).
- `rotateFeedToken` sets `token`, `token_rotated_at` and `updated_at` in one `UPDATE`.

## 2. The feed route

**File:** `src/app/api/calendar/feed/[token]/route.ts`
**Public URL:** `https://zo-bot.com/travel/api/calendar/feed/<token>.ics`

Not `/api/calendar/[token]`. A dynamic segment directly under `/api/calendar` would force the
proxy allowlist to distinguish the public feed from the management routes by *exclusion*; a
distinct `feed/` prefix makes both the proxy rule and the Cloudflare Access path exact
one-liners.

```ts
export async function GET(request: Request, ctx: RouteContext<'/api/calendar/feed/[token]'>) {
  const raw = stripIcsSuffix((await ctx.params).token);
  if (!isValidTokenShape(raw)) return notFound();

  const feed = getFeedByToken(raw);
  if (!feed) return notFound();

  const filters = parseFeedFilters(feed.filters);
  const items = buildCalendarItems({ userId: feed.userId });
  const kept = filterItems(items, filters, localToday());

  const body = buildCalendar(feed.name, kept.map(buildVEvent).filter(Boolean));
  recordFetch(feed.id, request.headers.get('user-agent'));

  return new Response(body, { headers: { /* below */ } });
}
```

`RouteContext<'…'>` is the Next 16 helper; types are generated by `next dev` / `next build` /
`next typegen`. A hand-written `{ params: Promise<{ token: string }> }` also works if the
generated type is not available.

**Export only `GET`.** Next answers 405 to every other method, which is what makes the proxy
bypass safe.

**Headers:**

| Header | Value | Why |
|---|---|---|
| `Content-Type` | `text/calendar; charset=utf-8` | |
| `Cache-Control` | `private, no-store, max-age=0, must-revalidate` | A stale cached copy behind Cloudflare would persist for up to a day and be indistinguishable from Google being slow |
| `X-Robots-Tag` | `noindex, nofollow, noarchive` | Defence in depth if the URL ever leaks somewhere crawlable |
| `Content-Disposition` | **omitted** | `attachment` makes some clients download instead of subscribe. The per-trip route keeps its own |

**404 for everything.** Malformed token, valid-shaped token with no row, and no such feed all
return an identical bare `text/plain` 404. Never 403 — that confirms a resource exists. Never
distinguish "wrong token" from "no such feed".

**No constant-time compare.** The unique index makes this a B-tree probe on a 256-bit secret.
Using `timingSafeEqual` would require `SELECT *` over every feed and comparing in JS — that
removes the index and adds nothing. Every failure path returns the same 404, there is no
early-exit oracle, and 2^256 is not brute-forceable through Cloudflare + nginx + Node jitter.
The cheap `isValidTokenShape` regex is the useful guard: it keeps junk out of SQL and the logs.

**No `export const dynamic`** — see `00-overview.md`. Leave a one-line comment saying why it is
absent.

## 4. Management API

All three under `/api/calendar/config` — **outside** `PUBLIC_PATH_PREFIXES`, so they stay behind
Cloudflare Access and behind the read-only gate. All wrapped in `withErrorHandling` from
`src/lib/api-helpers.ts`. All use unsafe methods, so `src/proxy.ts` returns
`403 {"error":"read_only"}` to non-admin users for free — no per-route auth code.

| File | Method | Body | Returns |
|---|---|---|---|
| `src/app/api/calendar/config/route.ts` | `PUT` | `{ name?, filters }` | The stored config (never the token) |
| `src/app/api/calendar/config/rotate/route.ts` | `POST` | — | `{ token, tokenRotatedAt }` |
| `src/app/api/calendar/config/preview/route.ts` | `POST` | candidate `filters` | `{ total, byKind }` |

**`parseFeedFilters` is the validator.** Do not add a Zod schema alongside it — two validators
for one shape will drift, and `parseFeedFilters` already drops unknown keys and defaults absent
ones. `PUT` runs the body's `filters` through it, then `serializeFeedFilters` to store, so
whatever lands in the column is always well-formed.

`name`: trim, cap at ~100 chars, fall back to the existing name if empty.

**`preview` is a POST despite being a read.** A read-only user cannot edit filters at all (the
whole control set is hidden), so a 403 is the consistent answer, and it avoids stuffing a JSON
blob into a query string.

**No `GET /api/calendar/config`.** The Settings page is an async server component and reads the
DB directly, exactly as it does for `gmail_tokens` (`settings/page.tsx:60-64`).

**Rotation is the only revocation mechanism, and it breaks BOTH subscriptions.** After it, the
old URL 404s and both subscribers' calendars freeze at their last successful fetch — Google does
not delete a subscribed calendar that stops resolving, it just stops updating. Both people must
delete and re-add. The Phase 3 confirm copy must say this.

## Verification

Local dev is port **3000** with basePath `/travel`. Get the token with
`sqlite3 local.db "SELECT token FROM calendar_feeds"` after hitting any page that calls
`ensureFeed` — or call it from a scratch script if Phase 3's UI does not exist yet.

1. `curl -s "http://localhost:3000/travel/api/calendar/feed/<token>.ics"` → 200,
   `content-type: text/calendar; charset=utf-8`, body starts `BEGIN:VCALENDAR`.
2. The same URL **without** `.ics` → identical body.
3. `curl -sI` shows **no** `content-disposition` header and `cache-control: private, no-store…`.
4. A well-formed but unknown token → **404**, `text/plain`. A malformed token (`abc`, or one
   with `/`) → **404**. Identical bodies. Nothing 403s, nothing 500s.
5. `curl -X POST`/`PUT`/`DELETE` on the feed URL → **405**. This is what makes the proxy bypass
   safe; verify it rather than assuming.
6. Two consecutive fetches with no edits are **byte-identical**.
7. The body validates at `icalendar.org/validator.html`.
8. `sqlite3 local.db "SELECT last_fetched_at, last_fetched_user_agent FROM calendar_feeds"` is
   populated and the UA is truncated.
9. **The proxy behaviour, for real** — not by reading the code. Run the production build with
   `ALLOW_NO_ACCESS_HEADER` **unset** and no `cf-access-authenticated-user-email` header:
   - the feed URL → **200**
   - `/travel/settings` → **403 Forbidden**
   - `PUT /travel/api/calendar/config` → **403**
   (PowerShell: `$env:NODE_ENV='production'`, then `npm run build; npm start`. Bash-style
   `VAR=x npm start` is a parse error in PowerShell.)
10. With `ADMIN_EMAILS` set to an address that is not yours and a
    `cf-access-authenticated-user-email` header for that address: the feed still 200s, but
    `PUT /api/calendar/config` and `POST .../rotate` both return
    `403 {"error":"read_only"}`.
11. `PUT` a filter set that excludes `unbooked`; re-fetch; the unbooked VEVENTs are gone and the
    rest are unchanged.
12. `PUT` deliberately malformed filters (`{"filters":"nonsense"}`, `{"filters":{"kinds":5}}`).
    The route responds 200 with defaults applied and the feed still serves — it must never 500.
13. `PUT` `{"filters":{"kinds":[]}}` → the feed returns **only the placeholder VEVENT**, not an
    empty calendar, and still validates.
14. `POST .../rotate` → the old URL now 404s, the new token 200s, `token_rotated_at` is set.
15. `npm run build` and `npm run lint` clean (11 pre-existing warnings).

**Done when:** all 15 pass — especially 5, 9 and 10, which are the three that prove the auth
change is scoped and did not open a hole.
